# B300 target and compatibility

The remote device and installed package are authoritative. The expected B300
target is Blackwell SM103 (compute capability 10.3), but verify rather than
hardcode it. This handbook's API baseline is CUTLASS 4.6.1, commit
`e05f953a5b3d38adc240df2ff928e0421c2abba3`.

## Probe only when needed

```python
print(torch.cuda.get_device_name())
print(torch.cuda.get_device_capability())
print(torch.__version__, torch.version.cuda)
print(getattr(cutlass, "version", "unknown"))
print(getattr(cutlass, "CUDA_VERSION", "unknown"))
```

Resolve compatibility in this order:

1. actual device/capability
2. installed CUTLASS/CuTe package
3. examples shipped with that package
4. local version-pinned recipes

An importable API is not proof that its instruction is legal. Compilation and
a real launch are the final checks. Do not install a different CUTLASS inside a
submission.

## Architecture rules

The target path couples:

- TMA transfers between GMEM and SMEM
- CTA clusters and optional multicast
- `tcgen05` MMA
- TMEM accumulators
- producer/consumer pipelines and warp specialization

Tile, cluster, stage count, SMEM/TMEM allocation, transaction bytes, barriers,
grid, and epilogue partitioning must form one valid configuration.

SM100 and SM103 examples are not automatically interchangeable. Start from a
dense Blackwell example for ordinary E4M3/E5M2 GEMM and an MXFP8 example only
when SFA/SFB are kernel inputs. The specialized SM103 FP4 Ultra example is not
an FP8 template.

Begin with one-CTA MMA, cluster `(1,1)`, non-persistent scheduling, an exactly
tiled shape, and the simplest epilogue. Add cooperation only after this works.
The common 128-thread block belongs to the local warp-specialized recipe, not to
all CuTe kernels.

## Remote response

Transport details live in `AGENTS.md`. Interpret fields separately:

| Field | Meaning |
|---|---|
| `success`, `exit_code` | service/process outcome |
| `stdout`, `stderr` | checks and diagnostics |
| `timed_out` | possible deadlock or excessive work |
| `device_time_ms` | directional profiler time; no controlled warmup |
| `profile_id`, `profile_error` | profile artifact/status |

Use the shared service modestly: small correctness cases first, then bounded
timing. A timeout on a tiny case usually means a pipeline bug, not a need for a
longer run.

## Gate

- Verify device/package when unknown.
- Use a matching dense or block-scaled operation.
- Enforce launch/resource/alignment constraints.
- Prove the path with compile plus launch.
- Establish correctness before performance.
