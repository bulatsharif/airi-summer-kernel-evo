# Remote B300 target

The remote service is the authority for the execution environment. “B300”
selects the expected Blackwell generation, but the reported device capability,
CUDA runtime, installed CUTLASS/CuTe package, and successful compilation decide
which APIs are usable.

## Expected target

The expected compute capability is 10.3, associated with the SM103 Blackwell
target used by B300-class systems. Treat this as a project expectation, not a
hardcoded fact:

```python
major, minor = torch.cuda.get_device_capability()
print(f"compute_capability={major}.{minor}")
```

Do not force an SM103-only path solely from the product name. A service image
may expose a compatibility target, a newer CUTLASS package, or a different
driver/toolkit combination.

The local documentation baseline is:

```text
CUTLASS release: 4.6.1
source commit: e05f953a5b3d38adc240df2ff928e0421c2abba3
```

This pins the concepts and example structure in the local reference bundle.
Exact symbols remain subject to the package installed remotely.

## Minimal environment probe

Probe only when existing run output is insufficient:

```python
import torch
import cutlass

print(f"device={torch.cuda.get_device_name()}")
print(f"capability={torch.cuda.get_device_capability()}")
print(f"torch={torch.__version__}")
print(f"torch_cuda={torch.version.cuda}")
print(f"cutlass={getattr(cutlass, 'version', 'unknown')}")
print(f"cutlass_cuda={getattr(cutlass, 'CUDA_VERSION', 'unknown')}")
```

If a CuTe symbol cannot be imported, inspect the installed package and examples
within the same environment. Do not create a permanent probe module or install
a replacement CUTLASS package in a remote submission.

Useful compatibility questions:

1. Is CUDA available?
2. What compute capability is reported?
3. Does `import cutlass.cute as cute` succeed?
4. Are the Blackwell `tcgen05`, TMA, pipeline, and TMEM helpers present?
5. Does the shipped example use the same import and launch conventions?
6. Does a minimal selected operation compile for the actual architecture?

## Compatibility hierarchy

Resolve conflicts in this order:

1. actual device and compute capability
2. installed CUTLASS/CuTe package
3. examples shipped with that installed package
4. these local, version-pinned recipes
5. remembered or external snippets

Use local references to choose the design. Use installed sources only to settle
exact signatures or release-specific spellings.

An API being importable does not prove that the chosen instruction is legal for
the target. Compilation and a real launch are the final capability checks.

## Blackwell execution model

The dense and block-scaled recipes in this bundle assume the Blackwell path:

- Tensor Memory Accelerator moves large tiles between GMEM and SMEM.
- CTA clusters allow multicast and cooperative execution.
- `tcgen05` MMA consumes supported operand layouts.
- MMA accumulators reside in tensor memory.
- epilogue warps move accumulator fragments from TMEM to registers, convert
  them, and store output.
- named producer/consumer pipelines coordinate asynchronous stages.

These pieces form one contract. Tile sizes affect:

- TMA descriptor shapes
- SMEM layouts and allocation size
- transaction byte counts
- MMA partitioning
- TMEM column allocation
- cluster multicast masks
- barrier participation
- output grid and epilogue partitioning

Do not copy only the MMA call from an example and invent the surrounding memory
protocol independently.

## SM100 and SM103 examples

SM100 and SM103 are related Blackwell targets, but examples are not
automatically interchangeable.

Use these rules:

- start from a dense Blackwell example for ordinary E4M3FN/E5M2 GEMM
- start from an MXFP8 block-scaled example only when SFA/SFB tensors are part of
  the operation
- use an SM103-specialized example only if its operation, types, and installed
  target match
- do not convert the specialized SM103 FP4 Ultra example into FP8 by merely
  changing tensor types
- preserve the selected example's architecture guards and `can_implement`
  constraints until each is deliberately reevaluated

If only an SM100 dense FP8 example matches the operation, it can be a structural
seed on an SM103 environment when the installed release supports it. Confirm by
compilation and execution rather than by assuming source compatibility.

## Resource and launch contract

Blackwell kernels can fail before execution because launch resources are
coupled. Check:

- block size matches the warp-role decomposition
- cluster shape satisfies power-of-two, size, multicast, and two-CTA rules
- dynamic/shared-memory allocation fits the target
- pipeline stages fit the chosen A/B/scale/epilogue layouts
- TMEM allocation fits the accumulator and optional scale factors
- grid dimensions agree with cluster and output tiling
- aligned dimensions and pointers satisfy TMA/MMA requirements

The local dense 4.6.1 recipe commonly launches 128 threads per CTA. That is a
property of that warp-specialized kernel structure, not a universal CuTe rule.

Start with:

- one-CTA MMA
- cluster `(1, 1)`
- non-persistent scheduling
- a simple output epilogue
- an exactly tiled shape

Add more architecture-specific coordination only after the baseline works.

## Remote runner contract

The parent `AGENTS.md` owns the current URL, API key environment variable,
submission command, profiler field, response schema, and profile download
command. Do not duplicate the secret or service URL in a submission.

Important response fields:

| Field | Interpretation |
|---|---|
| `success` | Service/process-level result |
| `exit_code` | Python process exit status |
| `stdout` | Explicit checks and measurement summaries |
| `stderr` | Import, JIT, compiler, launch, assertion, or runtime errors |
| `timed_out` | Possible deadlock, excessive compilation, or excessive work |
| `device_time_ms` | PyTorch Profiler device time; directional by default |
| `profile_id` | Identifier for a downloadable profile |
| `profile_error` | Profiling error, potentially independent of process result |

The service is shared. Keep submissions bounded. Do not run an unattended tile
search, a large Cartesian product of configurations, or an indefinitely
repeating benchmark.

## Safe development sequence

1. Verify environment only if unknown.
2. Compile the smallest matching native FP8 configuration.
3. Run one exactly tiled correctness case.
4. Add multiple K tiles.
5. Add the remaining required shapes and layout cases.
6. Add scale tensors for a block-scaled operation.
7. Add TMA output or a richer epilogue.
8. Measure a warmed baseline.
9. Try a small number of justified tile/stage/cluster candidates.
10. Repeat the final candidate and preserve the known-correct baseline.

A remote timeout during a tiny case is evidence of a pipeline or collective
protocol bug. It is not evidence that the service needs a longer benchmark.

## Compatibility checklist

- [ ] Actual compute capability was observed or is already known.
- [ ] Installed CUTLASS/CuTe version is known well enough to select APIs.
- [ ] The closest installed example matches dense versus block-scaled semantics.
- [ ] The operation class supports the requested FP8 types.
- [ ] SM100/SM103 specialization assumptions are explicit.
- [ ] Launch block, cluster, SMEM, TMEM, and stages form one valid configuration.
- [ ] A small real compile and launch validate the selected path.
- [ ] The remote file is self-contained and reads no secret directly.
- [ ] Correctness precedes performance measurement.
- [ ] Shared-service use remains bounded.
